# chrome-chat

A familiar, modern chat-app interface running entirely on Chrome's built-in Gemini Nano — no server, no API key, no account, and nothing you type or attach is ever sent to a server of ours. (One disclosed exception: pasting a recognized public link — GitHub, Wikipedia, Hacker News — fetches that page's own public data directly from its own API, never through anything of ours. See Features.) Live at https://nlade-core.github.io/chrome-chat/

## Why this exists

Built directly on two pages from [`pages-lab-ai`](https://github.com/nlade-core/pages-lab-ai): `chat-threads` (multiple saved conversations in `localStorage`, replayed into the model only on demand) and `assistant` (markdown rendering, further chat polish). This repo takes that same underlying mechanism and gives it the full-height app-shell interface modern AI chat apps use — a dark sidebar of past conversations, centered chat column, bubble-less assistant replies — rather than `pages-lab-ai`'s boxed-panel, scrolling-document house style.

## Features

- Multiple saved conversations, listed in the sidebar, backed by `localStorage`, each given a real generated title (a genuine short model summary of your first message, not just a truncated substring of it) once its first reply finishes
- Streaming replies with Markdown rendering
- Copy a finished reply to the clipboard
- Stop generation mid-stream
- Regenerate the last reply
- Edit any previous message (not just the last) and resend — non-destructive: nothing is touched until you confirm, and a clear warning shows how many later messages would be removed if you're editing an earlier one
- A warning once a conversation gets close to the model's context limit
- Delete a saved conversation with a two-click confirmation (no accidental, un-undoable deletes)
- Rename a saved conversation inline
- Search saved conversations by title, generated summary, *and* full message content — matches each word in the query independently (so "japan trip" finds a message that says "trip to Japan"), and ranks title/summary matches above content-only ones instead of ordering purely by recency
- If that instant search comes up completely empty, a fallback AI-assisted pass kicks in automatically: one model call carrying every thread's title and summary asks which ones are relevant to what you typed, catching conversations the literal search couldn't (different wording, no shared words at all). Results show in a clearly separate "found by meaning" section, never blended silently into normal matches; a "searching more broadly…" note shows while it's working. Normal typing that finds a real match never touches the model at all.
- A "scroll to bottom" button that appears once you've scrolled up mid-conversation
- A brand-new conversation starts with its composer centered in the middle of the screen alongside the greeting, docking to the bottom the instant you send the first message — matching the landing-then-dock pattern common in modern chat interfaces
- While that landing screen shows, the model's session is silently pre-warmed in the background if it's already known to be available — so your first message doesn't also pay for session setup. If a real download would be needed instead, the landing screen says so upfront rather than staying silent until you send.
- **Conversation forking**: editing a message offers "Fork" alongside "Save & submit" — instead of overwriting, it creates a brand-new conversation with everything before the edit preserved, leaving the original completely untouched. Forked conversations collapse into a single sidebar entry (the original's title + a count badge); expanding it shows every version — original and forks alike — as neutral peers with a relation tag and last-updated time, no version auto-selected as "main". Forking a fork still traces back to the true original, however deep the chain.
- **Multimodal input**: attach an image or audio clip alongside your message. The attachment persists across reloads and browser restarts, same as everything else — the real image/audio renders again the next time you open that conversation, not just a memory of it having existed.
- **Response timing**: each finished reply shows how long it actually took — time to first token and total duration — a quick, honest answer to "is this slow, does an image slow it down," measured live rather than assumed. In-memory only, not saved across a reload.
- **Safe background generation**: switching to a different conversation — or starting a new chat — while a reply is still streaming no longer loses or corrupts anything. The reply keeps generating and saves correctly to the conversation it actually belongs to; a small dot in the sidebar shows which thread is still working while you're looking at something else. Gemini Nano is one shared on-device model, so a second reply generating at the same time as another will likely wait its turn rather than truly run in parallel — an honest "Waiting on another reply…" note shows while that's happening, instead of silently looking stuck.
- **Manual Summarize and Condense**: Summarize reads the whole conversation and refreshes its title plus a stored summary, without touching the live session. Condense goes further — summarizes the conversation, then restarts the model fresh from just that summary, so a long thread can keep going instead of hitting its context limit and being abandoned. The full transcript stays visible either way; nothing you said or received is ever hidden. A proposed new title after condensing is always asked for, never applied silently.
- **Context-usage meter**: a small color-coded bar and percentage in the header show how much of the model's context window the current conversation has actually used, not just a warning after the fact.
- **About panel**: a plain-language explainer (what runs locally, what's stored and where, requirements, link to the source) for a casual visitor who lands on the live site without going through GitHub first.
- **Linked context from open APIs (v1: paste-detection)**: paste a link to a GitHub repo, a Wikipedia article, or a Hacker News item into the composer, and chrome-chat automatically fetches that page's public data straight from its own API (no server of ours involved) and hands it to the model alongside your message — a small chip shows what was fetched, and a citation link stays attached to the sent message so it's clear where the extra context came from. A "Show what was fetched" dropdown under that citation shows the *exact* plain-text block that was actually sent to the model — nothing hidden, nothing to take on faith. Removing the link from your text (or the × on the chip) drops it again before you send. A failed fetch (rate-limited, not found, or any other error) shows a specific message rather than the chip just silently vanishing. This first pass only recognizes a link you've pasted yourself; a natural next step is letting the model decide *on its own* when it needs to pull one of these in, rather than only reacting to a URL already sitting in the box.
- **`/wiki <topic>` slash command**: don't have (or don't want to look up) the exact article link? Type `/wiki` followed by whatever you're after — e.g. `/wiki jarvis island`, or a genuine question like `/wiki who invented the telephone` — and chrome-chat resolves it to a real article via Wikipedia's own full-text search, skipping past disambiguation pages ("may refer to..." lists) in favor of the next real candidate, then fetches and cites it exactly like a pasted link would. The whole message is treated as the command, so put your actual question in a follow-up once it resolves. Add `full` right after `/wiki` (e.g. `/wiki full eiffel tower`) to pull in the entire article instead of just the short summary, for when the summary genuinely doesn't have what you need — capped at 8,000 characters with the truncation disclosed for a long article, rather than either cutting it off silently or blowing past the model's context budget. Add `image` instead (e.g. `/wiki image eiffel tower`) to pull in the article's real lead photo — it shows up as a genuine attachment (not just a description) and is handed to the model as actual multimodal input, exactly like a manually-attached image.
- **`/wiki:fr <sujet>` — other language editions** (2026-09-26 07:47): the same command (and `/wiki:fr full`, `/wiki:fr image`) against French Wikipedia. Each language edition is its own wiki with its own articles and search index, but the same API shapes, so switching language is switching host (`fr.wikipedia.org`). Type the query in that language — an English question on French Wikipedia returns unrelated articles (confirmed live). The article goes to Gemini Nano untranslated (French is one of the Prompt API's documented languages), with an instruction to reply in whatever language you wrote in. Only languages with an entry in `WIKI_LANGS` are enabled (back-matter headings and question stopwords are language-specific); `/wiki:de` etc. say so rather than half-work. Pasted links already work for any language.
  - (2026-09-26 07:54) **English queries work too**: an English-looking query (judged by function words alone, no model) is searched on English Wikipedia and each hit hopped to its French article via Wikipedia's own interlanguage links, in the same request — `/wiki:fr who invented the telephone` → Téléphone (via "Telephone"). Hits with no French article are dropped.
- **Going deeper after `/wiki`** (2026-09-26 07:54): the latest Wikipedia article in a conversation stays open. Its full text is prefetched in the background as soon as it resolves; each follow-up you type is matched against the sections the model hasn't been given yet, and the best one or two (≤3,000 characters) ride along with that message — shown in the chip before you send (📖 Edinburgh › Economy), removable with ×. No match adds nothing; "tell me more" adds the next unread section. Sections are never sent twice. This keeps context growth proportional to what the conversation actually asks about, rather than loading a 40–75k-character article a small on-device model can't hold. Which sections were already given is read back off earlier turns' fetched text, so it needs no new storage and survives reloads.
  - (2026-09-26 08:15) **Across languages, fastest-first.** Each follow-up escalates only as far as it needs to: (1) word matching against unread sections, instant; (2) if the question and article are in different languages, the question is first translated into the article's language with Chrome's **Translator API** — a separate small on-device translation model, not Gemini Nano — purely for matching (the model still sees what you typed, and reads French natively); (3) only at send time, only if nothing matched and the message is a question, Gemini Nano is shown the unread section *titles* (~300 tokens, no content) and picks one via a structured single-integer reply, on a throwaway session. That last step never runs while you type. Translation packs download only on a user gesture (send), in the background — a message never waits on a download. Untranslated cross-language word matching is skipped entirely, since it produced false matches.
- **Plain `/wiki` picks the edition from your language** (2026-09-26 08:15): `/wiki qui a construit la tour eiffel` searches French Wikipedia with no `:fr` needed; English or undetectable (a bare name) stays English. `/wiki:en` / `/wiki:fr` always win, and the language-link hop works in both directions (`/wiki:en qui a inventé le téléphone` → Invention of the telephone). Language detection is function words plus French accents — instant, no model.
- **Declared session languages** (2026-09-26 08:15): chat sessions now declare `en`/`fr` as expected input/output languages (as Chrome's own warning asks), only after `availability()` confirms the build supports it — otherwise created exactly as before.
- **Finding the article at all, and the best language for it** (2026-09-26 08:53): every `/wiki` also checks the paired edition (English ↔ French) for an exact title, in parallel — full-text search nearly always returns *something*, so "no results" never caught a topic only one edition covers. An article that exists only in the other edition is used as-is and labelled (`Les Films de Pierre (fr) -- no en article`). After resolving, the paired edition's size is checked in the background, and a clearly fuller one (≥1.5×, by wikitext bytes) is offered as one click — "Fuller in French" on Montmartre or Château de Chambord, "Fuller in English" on Édimbourg. Never delays the answer.
- **`/wiki compare <topic>` — where editions disagree or have holes** (2026-09-26 08:53): puts the English and French articles side by side for the model. Code does the reliable part: sizes, both section lists, and years dated in one article but never mentioned in the other, each with its sentence (bibliography page ranges filtered out) — on Edinburgh, the Wars of Independence occupation (1291–1341) and the 1582 university founding are absent from the French article; Flodden (1513), the botanic garden (1670) and the Bank of Scotland (1695) from the English. The model then lists facts stated differently and coverage gaps, framed as leads for an editor to check, not verdicts; asked in French, it answers in French. A topic with no counterpart at all is reported as a coverage gap.
- **Follow-up section choice, re-ordered by measurement** (2026-09-26 08:53): a same-language *heading* match is used instantly; otherwise, at send, the model picks from the unread section titles (any language); translated/plain word matching is the fallback. A weak word-match preview shown while typing is re-decided at send rather than reused. When the question's language differs from the source's, an explicit "Reply in English." / "Réponds en français." is placed after the source text.
- **A `/wiki` question gets its answer section in the first turn** (2026-09-26 09:21): the summary is the quick pull, and the section that answers the question rides along in the same message, chosen exactly like a follow-up (heading match instantly; otherwise the model picks at send). `/wiki how tall is the eiffel tower`, `/wiki when was edinburgh castle besieged` → Lang Siege, `/wiki quelle est la hauteur de la tour eiffel` → Données techniques. A bare topic (`/wiki edinburgh`) stays summary-only. Later follow-ups continue from the full article and never repeat it. Question-style queries also resolve to their *subject* now: a result whose title appears in the question ranks first (`what is the economy of edinburgh based on` → Edinburgh, not Market economy), and when full-text search can't see the subject at all (it needs every word — `is montmartre worth visiting` returned Barbara La Marr) the question's longest content words are tried as exact titles, in parallel, only in that case.

- **Offline Wikipedia in the page — no install** (2026-09-27 14:02): on the public site, open About → **Connect a .zim file…** (or run `/wiki:offline <question>` and use the chip's **Choose .zim file…**), pick a Kiwix ZIM (e.g. English Wikipedia *mini*, 14.4 GB, from [library.kiwix.org](https://library.kiwix.org)), and `/wiki:offline` answers from it. The file is read **in place** by Kiwix's libzim compiled to WebAssembly ([`vendor/libzim/`](vendor/libzim/), GPL-3.0, 2.3 MB, loaded only once a file is connected), running in a Web Worker: never uploaded, never copied, read in slices straight from disk. The file handle is remembered (IndexedDB), so a returning visitor only re-allows reading it. Plain `/wiki` uses it automatically when the browser is offline. Offline answers never trigger online follow-ups. Measured in headless Chrome 154 on the 14.4 GB file: opens in ~0.7 s (18.1 M entries); the 14-question offline set picks the **same article as the local-server route 14/14** (`eval/offline-parity.html`), at 54–728 ms per question in the page vs 11–367 ms via the native server; zero requests beyond the page's own origin, including a no-network run where plain `/wiki` answered from the file. Making it fast needed one change shared by both routes: exact Wikipedia-style paths (`Eiffel_Tower`, `University_of_Edinburgh`, `World_War_II`) are tried before the title-suggestion index, which in WebAssembly takes 1.5–2.6 s for a common single word ("capital", "scotland") vs 6–50 ms for an exact path; and longer phrases are checked first, stopping at the first length with a real title. Not yet run with real Gemini Nano; the file-picker dialog itself was stood in for in the automated test (headless Chrome can't drive it).
- **Offline Wikipedia: `/wiki:offline <question>`** (2026-09-27 13:07): the same pipeline against a local Kiwix copy of Wikipedia instead of wikipedia.org. Run `python3 offline/serve.py` (needs a ZIM file and [kiwix-tools](https://download.kiwix.org/release/kiwix-tools/); defaults look in `~/Downloads/kiwix/`), open http://localhost:8080. It serves chrome-chat and proxies `kiwix-serve` under `/kiwix/` on the same origin, and logs every request — with Gemini Nano on-device and Wikipedia on disk, a whole question-and-answer round trip never leaves localhost. Plain `/wiki` also falls back to it when the browser is offline. Article choice is tuned for Kiwix's weaker full-text search: exact title, then the longest run of question words that is an exact title ("how tall is the eiffel tower" → Eiffel Tower, "when did world war ii end" → World War II), then full-text; disambiguation pages and sub-200-character stubs are skipped. The model gets the article's intro plus its infobox as "label: value" facts. Checked against the 14.4 GB English *mini* ZIM (intros + infoboxes only): 13/14 questions landed on the intended article (the odd one out, bare "mercury", picks Mercury poisoning — alternatives offered), 12–700 ms per lookup, 298 requests served with none leaving the machine; five answers through the Gemma stand-in were all correct, including "when was edinburgh castle besieged" (the intro cites 26 sieges) and a French question answered in French from the English copy. A mini ZIM has no later sections, so offline follow-ups can't go deeper than the intro. Not yet run with real Gemini Nano.

- **Guided tour: what the model can do, and where it stops** (2026-09-27 18:26): open [`?tour`](https://nlade-core.github.io/chrome-chat/?tour) or the sidebar's **Take the tour**. A scorecard at the end, with copyable results. The tour drives the real app — it fills the message box and the visitor presses send — through `window.chromeChat` and two events (`chat:reply`, `chat:context`); it loads only on request (`tour/`, ~20 KB). Scoring is plain code against a bundled answer bank ([`tour/bank.js`](tour/bank.js)), never the model grading itself.
  - *How the questions were chosen:* 12 questions, each with a numeric answer in its Wikipedia article's opening section, were committed before any calibration run (a36d673); [`eval/tour.mjs`](eval/tour.mjs) then ran each 5× through the Gemma stand-in, cold and with the opening section attached. Trap: the Scott Monument article has no visitor figures; the stand-in said so 5/5.   - *Verified* in headless Chrome with a scripted stand-in model, all five chapters end to end: an always-right model scores every checkpoint green; an always-wrong one gives "still wrong" with a source, "filled the gap" on the trap, and forced format 3/3 clean but 0/3 right; chapter 5 answered with the network emulated off and 0 requests; no page errors; without `?tour`, no tour files are requested. ## Requirements

**Branded Google Chrome, desktop, only.** Gemini Nano's weights are proprietary to Google's own Chrome binary — open-source Chromium doesn't have them, so this won't produce real answers in Chromium-based non-Google browsers or automated test browsers. The Prompt API itself needs a recent Chrome (138+); if the sidebar shows "not in this browser" or "needs download," that's what's happening.

## Architecture

Single static `index.html` — zero build step, zero framework, zero backend. Everything runs in your browser:

- **Model:** `window.LanguageModel` (Chrome's Prompt API). A session is created when you send a message or open a saved conversation — with one deliberate exception: on a brand-new chat's landing screen, if the model is already confirmed available (no download needed), a session is silently pre-warmed in that dead time so your first message doesn't also pay for session setup. Never happens if a download would actually be required; that case is disclosed upfront instead.
- **Storage:** `localStorage`, namespaced `chrome-chat:`, for everything text-based — an index key (`chrome-chat:index`) holds `[{id, title, updatedAt}]`, each conversation's messages live under their own `chrome-chat:thread:<id>` key. Attachment *blobs* live separately in IndexedDB (`chrome-chat-attachments`, one object store keyed by a generated id) since binary data doesn't fit `localStorage`'s small text-only quota — a message references its attachment by that id rather than embedding it. Deleting a conversation deletes its attachment blobs too, unless a fork still references the same one (forks can share pre-fork attachments — checked before any blob is actually removed).
- **Restoring a saved conversation:** its messages render immediately (free, just redrawn from storage) — the model itself is only re-primed with that history via `initialPrompts` at the moment you open it, never speculatively for conversations you haven't clicked on.
- **Markdown:** rendered via `marked.js`, with model output escaped *before* parsing — literal HTML/`<script>` in a response renders as inert text, never executes.
- **Fork lineage:** two extra fields on a thread's index entry — `forkedFrom` (immediate parent id) and `forkRoot` (the ultimate original ancestor, inherited transitively). A fork of a fork still resolves back to the true root in one lookup, without walking the chain.
- **Per-conversation isolation:** each conversation (including a brand-new one, from the instant its first message is sent) has its own session, its own message history, and its own in-flight-generation state, held independently of whichever one is currently displayed. Switching what you're looking at never touches another conversation's live state.
- **Idle-session caching:** the last few conversations you've stepped away from stay warm instead of being torn down immediately — revisiting one of them skips the cost of recreating a session and re-feeding its whole history back in. Bounded to a handful at a time (least-recently-used ones fall out first) so it doesn't grow without limit over a long browsing session.
- **Linked-context fetching:** a small allowlist maps a recognized URL pattern (GitHub repo, Wikipedia article, Hacker News item) to that service's own public, CORS-open API endpoint — confirmed directly via `curl` for all three before building this, rather than assumed. Detection is debounced text-matching against the composer's own input, not a model decision; the fetched result is handed to the model as its own text turn ahead of your message, and the exact same text is persisted with the saved message (inspectable via its "Show what was fetched" dropdown) — though it isn't replayed back into the model on reopening a saved conversation later (the same limitation attachments already have on reopen; only the live turn it was originally sent on ever actually saw it). The `/wiki <topic>` slash command reuses this same fetch-and-format pipeline, adding one resolution step in front: Wikipedia's own full-text search API (`action=query&list=search` — also confirmed CORS-open, via its `origin=*` parameter specifically — without it there's no CORS header at all) turns free text into a real article title, which then flows through the exact same summary-fetch/formatter/citation path as a pasted link. Deliberately not the `opensearch` endpoint (tried first, then replaced): that one only matches article titles — the same mechanism behind Wikipedia's own search-box autocomplete dropdown — so a genuine question like "who invented the telephone" came back empty. Full-text search matches actual article content, the same thing Wikipedia's site falls back to once you hit Enter/Search rather than picking a suggestion.
- **Disambiguation-page skipping (`/wiki`):** `resolveWikiCandidates(query, limit)` requests up to 3 full-text search results instead of just the top one, since the top-ranked match is sometimes a disambiguation page (a bare "may refer to..." list) even when a good, real article sits right below it in the results — the real case that motivated this: `/wiki noting` ranked "Note" (disambiguation) above "Mental noting" (the actual relevant article). The search runs as a `generator=search` with the `disambiguation` page prop attached, so each candidate comes back already flagged (a real, first-class page property MediaWiki sets — not inferred or guessed); `resolveWikiSlashCommand` takes the first unflagged one by search rank and fetches only that one's summary. (Originally it fetched every candidate's summary in turn to check its `type` field — up to 3 extra round trips on an unlucky query; replaced 2026-09-26 07:27.) If every candidate checked turns out to be a disambiguation page, it throws a specific error naming which page, rather than silently sending a useless "may refer to" list as model context.
  **Known limitations, worth knowing before extending this:** the candidate limit (3) is a chosen default, not tuned against real failure rates — it could be raised if disambiguation collisions turn out to be more common than expected. Skipped candidates aren't surfaced anywhere — if it skips "Note" and lands on "Mental noting," there's no visible trace of what else it considered besides the resolved title in the citation. And when multiple *real* (non-disambiguation) candidates are all plausible for a genuinely ambiguous query, it silently takes the first one rather than asking — that's the "picker UI" item already listed under Roadmap below, not yet built.

## Roadmap

**Recently shipped, in order:** conversation forking → multimodal input → durable IndexedDB attachment storage → a real per-thread data-loss/corruption fix for switching threads mid-reply → an idle-session LRU cache → a centered landing composer → landing-screen session pre-warming → generated conversation titles → manual Summarize/Condense + a context-usage meter → honest cold-start messaging → multi-word/summary-aware/relevance-ranked search → the queued indicator now seeing title-gen/Summarize/Condense contention too → a security/robustness pass (a real XSS fix, quota-crash guarding, an attachment size cap) → an AI-assisted search fallback for queries the literal search can't match → an in-app About panel → linked context from open APIs (paste-detection v1: GitHub, Wikipedia, Hacker News) → an inspectable "Show what was fetched" dropdown → friendly error messages on a failed fetch → the `/wiki <topic>` slash command → a race-condition fix so sending can't outrun a pending fetch → a switch to full-text search (handles real questions, not just titles) → disambiguation-page skipping → `/wiki full` for the complete article → `/wiki image` to pull the article's lead photo in as real multimodal input → (2026-09-26 07:27) a Wikipedia pipeline tightening pass: fetched context survives session rebuilds, a grounding instruction, one-call disambiguation check, more robust link detection, cleaner `/wiki full` truncation, and an identifying `Api-User-Agent` header → (2026-09-26 07:39) exact-title-first resolution, a "Not it?" article picker, revision-pinned CC BY-SA citations, and question-targeted section selection for `/wiki full`.

**Next candidates, roughly in priority order:**

1. **Natural-language triggers for linked context** (e.g. "check wiki for X"), as a second layer on top of the `/wiki` slash command above rather than a replacement for it — same template this project already uses for search (literal match first, AI-assisted fallback only when nothing explicit matched): a plain-language request would surface what it thinks you meant and let you confirm, rather than silently guessing and risking a wrong or wasted fetch. Reuses the same search-then-fetch pipeline `/wiki` already proved out; the new part is intent detection. Not started yet.
2. **Model-driven (fully dynamic) API fetching.** The model itself deciding mid-conversation that it needs to pull in a GitHub repo, a Wikipedia article, or similar — without any explicit command or trigger phrase from you at all. A real design task (when to trigger it, how to disclose/confirm it before the fetch happens), not started yet.
3. **Richer Wikipedia context types**: `/wiki image` (lead photo, tied into the existing multimodal image-input support) is shipped. "Related articles" as originally envisioned can't be built the way it was planned — Wikipedia's `/page/related/{title}` endpoint is confirmed decommissioned by Wikimedia, so that would need a different data source (e.g. category overlap, or search-based similarity) if it's still wanted. A picker when a query resolves to multiple plausible *real* articles is now shipped ("Not it?" alternatives in the chip). `/wiki:fr` is shipped; further languages need a `WIKI_LANGS` entry each. Still open: model-assisted section choice for `/wiki full` where plain term overlap misses synonyms.
4. **Conversation export.** Not designed yet.
5. **Theme toggle.** Not designed yet.
6. **Cross-tab write-locking.** Two tabs open on the same saved conversation can silently overwrite each other's save (a `navigator.locks`-based fix is designed, just not built — see project notes). Low priority for a single-user tool; revisit if it's ever actually hit in practice.
7. **The original "differentiated" tier, unstarted:** a live zero-network-requests indicator, Pyodide-based tool use, a thinking-mode toggle. All just named candidates so far, none designed.
8. **True semantic (embedding-based) search, parked pending a real API.** Chrome has a proposed on-device Embedding API (generates vector embeddings locally, aimed squarely at semantic search/RAG) — but as of writing it's at "Intent to Prototype," the earliest stage of Chrome's shipping process, not available in any released Chrome build. A separate embedding model via a JS library would work today, but that's a real identity shift for a project whose whole pitch has been "100% Gemini Nano, zero extra dependencies" — worth a deliberate decision, not a quick add. Revisit once Chrome's own API actually ships. (In the meantime, search already got two real upgrades without it — see Features above: a smarter literal search, and an AI-assisted fallback using the model itself rather than embeddings.)
